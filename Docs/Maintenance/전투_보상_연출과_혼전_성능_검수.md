# 전투·보상 연출과 혼전 성능 검수

Unity 6000.0.59f2와 Windows D3D11 플레이어를 사용했다. 기준 PC는 Ryzen 9 9950X3D와 RTX 4060 Ti다. 구현·검증 단위는 [7단계 계획](전투_보상_연출과_혼전_성능_계획.md)과 대응한다.

## 성능 검증 방법

- 시드 907의 실제 웨이브에서 네 마리와 그 적 종류를 확인했다. 같은 종류의 실제 프리팹으로 1·4·8·16마리의 통제된 전투를 구성했다. 이동, 동시 생성, 0.25초 간격 동시 피격, 3초 간격 동시 처치를 각 60초 측정했다. 이 시험에서 처치는 적 사망과 파편을 실행한다. 방 상자·드롭·습득은 별도 플레이 모드 검사로 확인했다.
- 배포 설정의 측정용 플레이어에서 GPU 타임스탬프와 프레임 간 실제 경과 시간을 수집했다. 전후 각 3회의 중앙값을 비교하며, 단 한 번이라도 길었던 프레임은 별도로 집계했다. 개발 빌드의 할당과 프로파일러 표본은 따로 해석한다.
- 전환은 메뉴→마을, 첫 던전, 실제 층 포탈, 보상 후 마을 복귀, 던전 재입장을 수행한다. 씬 활성화·맵 준비·플레이어 준비·입력 반환을 따로 기록했다. 연속된 두 관측 시점 모두 팔레트 페이드가 1일 때만 완전히 가려진 프레임으로 집계했다.
- 적 경로의 유효성, 타격 몸 재질의 속성 갱신, 이펙트 메시 갱신, 줌 중 HUD 글꼴의 재계산을 줄였다. 방 인스턴스 생성은 기존 타일 병합과 같은 프레임 예산으로 분산했다. 처음 여는 씬은 팔레트 페이드가 한 프레임 완전히 덮은 뒤 스트리밍한다. 이미 준비했던 씬은 페이드·포탈 연출 중 스트리밍을 시작한다. 플레이어와 맵이 준비된 뒤 입력을 반환한다.
- `Tools/Invoke-UnityVerification.ps1 -Suite CombatPolish`가 재현 진입점이다. `Tools/Verification/Compare-CombatPolish.ps1`은 전후 장치·시드·표본 시간을 검증한 뒤 CSV를 쓴다. 내장 GPU 실기기는 이번 측정 환경에 연결돼 있지 않았다.

## Windows 실측

전후 각 3회, 조건당 60초로 총 96구간을 기록했다. 아래 전투 표의 CPU·GPU p95와 프레임 p99는 세 실행의 중앙값이다. 최악 열은 세 실행 전체의 최대값이다. 단위는 밀리초다.

| 16마리 시험 | CPU p95 전 → 후 | GPU p95 전 → 후 | 프레임 p99 전 → 후 | 최악 전 → 후 |
| --- | ---: | ---: | ---: | ---: |
| 이동 | 3.49 → 3.23 | 3.67 → 3.26 | 4.37 → 3.64 | 32.27 → 10.07 |
| 동시 생성 | 3.25 → 2.40 | 3.60 → 2.48 | 4.34 → 3.79 | 34.69 → 13.77 |
| 동시 피격 | 6.98 → 5.95 | 7.10 → 5.95 | 9.10 → 7.51 | 48.76 → 8.61 |
| 동시 처치 | 1.83 → 1.52 | 2.46 → 2.17 | 4.89 → 4.57 | 31.10 → 11.43 |

변경 후 48개 구간 중 CPU·GPU p95 13.3ms 또는 프레임 p99 16.7ms를 넘긴 구간은 0개였다. 33.3ms 초과 프레임은 총 0개였고, 가장 긴 프레임은 13.77ms였다. 변경 전 바이너리는 이 초과 횟수를 기록하지 않아 최악값과 백분위만 직접 비교할 수 있다. 변경 전 일부 구간에는 이 PC의 격리 에디터 빌드·검사가 겹쳤다. 최악값 차이 전부를 게임 코드에 귀속할 수 없다.

전환 전용 플레이어 6회를 순서대로 실행했다. 변경 후 15회 전환에서 화면이 보이는 동안 33.3ms를 넘긴 프레임은 0개였다. 전체 최악은 72.27ms였다. 씬 활성화와 맵 준비 구간의 긴 프레임은 검은 페이드 중에도 입력 반환을 늦출 수 있다.

두 파티클 백엔드의 저·중·고 품질과 자연 발생 전투를 각각 60초 실행했다. 자연 전투의 프레임 p99는 8.40ms, 최악은 17.48ms였다. 자연 전투 기록은 `active dungeon encounter peakActors=4 successfulHits=239`다.

개발 빌드 변경 전 16마리 피격에서는 프레임 p99 7.69ms, 최악 22.48ms, 프레임당 관리 할당 p95 548바이트를 기록했다.

개발 빌드 변경 후 16마리 피격에서는 프레임 p99 9.63ms, 최악 20.56ms, 프레임당 관리 할당 p95 436바이트를 기록했다.

## 최종 전환과 종료 진단

- 처음 여는 던전까지 페이드 도중에 읽었던 중간 빌드에서 92.75ms의 가시 프레임을 발견했다. 첫 방문과 재방문의 스트리밍 시작 시점을 나눈 최종 빌드에서는 첫 던전의 가시 프레임 최대가 1.95ms였다. 일시정지 상태에서의 페이드 해제, 중복 이동 차단, 튜토리얼과 마을 도착도 검사했다. 이전 파란 로딩 바를 재생성하던 도구는 `Legacy/Rendering/CombatPolish`에 보관했다. [페이드 회귀 검사](../../Logs/Verification/CombatPolish/fade-contract.log)
- 마을의 고정 허수아비가 이동용 NavMeshAgent를 상속해 마을 진입마다 오류가 발생했다. 허수아비 프리팹에서 에이전트를 껐다. 재측정한 세 실행 모두 첫 마을 진입과 복귀에서 해당 오류가 사라졌고 같은 허수아비에 대한 실제 공격 검사는 통과했다.
- 개발 플레이어 종료 시 Unity 2D Animation 10.2.1의 GPU 스키닝 대체 버퍼에서 경고 1건이 발생한다. 격리 빌드에서 패키지 버퍼를 명시적으로 해제한 대조 실험에서는 0건이었다. 두 실험 모두 게임이 만든 GPU 입자 버퍼의 생성과 해제를 확인했다. 대조 실험용 패키지 내부 호출은 개발 진단 빌드에만 들어 있다. ## 연속 층 진행과 적 밀집도

Ryzen 9 9950X3D와 RTX 4060 Ti에서 Windows D3D11 플레이어를 1280×720으로 실행했다. 논리 프레임은 640×360이고 시드는 907이다. 표는 시드 907의 첫 전투 방에서 얻은 적 종류로 16개체를 구성한 각 5초 구간의 전체 프레임 시간이다. 각 조건을 한 번씩 실행했으므로 최댓값은 단일 프레임의 관측치다. [수정 전](../../Logs/Verification/FloorCrowd/before-crowd.json) · [수정 후](../../Logs/Verification/FloorCrowd/Verified/matrix-1.json)

| 동작 | p95 전 → 후 (ms) | 최댓값 전 → 후 (ms) |
| --- | ---: | ---: |
| 이동 | 9.02 → 7.50 | 11.71 → 10.10 |
| 동시 생성 | 9.07 → 7.41 | 17.33 → 13.67 |
| 반복 동시 피격 | 9.54 → 8.00 | 10.49 → 14.09 |
| 동시 처치 | 6.70 → 6.45 | 12.21 → 14.54 |

1층에서는 URP 지형 그림자 컴포넌트 435개 중 36개, 4~6층에서는 862개 중 69개가 점광원 도달 범위에 있었다. `RoomShadowCasters`는 조명의 위치나 반경, 사물의 월드 변환이 바뀌면 다시 판정한다. 점광원 범위로 계산할 수 없는 광원에서는 기본 처리를 복원한다. 조명이 가까워졌다가 멀어지는 검사와 마을·던전의 방향별 지형 그림자 캡처를 통과했다. [혼전에서 렌더링 요소별 비용을 분리한 실험](../../Logs/Verification/FloorCrowd/diag.json) · [플레이 모드 그림자 검사](../../Logs/Verification/FloorCrowd/PresentationRegressionCheck.Run.log)

매 층 일반 전투 방 한 곳을 실제 피해로 클리어하고 게임의 층 이동 경로로 다음 층에 진입했다. 모든 입구에서 이전 층의 런타임 내비게이션 데이터와 살아 있는 적은 0개였으며, 상주 루트 9개, 게임 프레임·바닥 마스크·GPU 파티클 필드는 각 1개였다. 같은 배치인 4~6층의 머티리얼·메시·텍스처 수는 각각 42·1,006·168개로 일정했다. GC 회수 후 관리 메모리는 22.65~22.68 MB, Unity의 전체 할당 메모리는 242.86~242.90 MB였다(십진 MB). GC는 측정 도구에서 프레임 시간 구간이 끝난 뒤에만 요청했다. [연속 층 전투 검사](../../Logs/Verification/FloorCrowd/Verified/floors-1.json)

32·64마리 부하 검사는 각 동작을 8초씩 측정했다. 64마리의 이동·피격 p95는 각각 9.96·11.29ms였다. 검사 도구가 유닛 64개를 직접 한 프레임에 교체하면 최악 38.16ms가 걸렸다. 실제 전투 방은 배치 후보 탐색·예고·생성을 분산하고, 마지막 적이 생성된 뒤에 웨이브 완료를 판정한다. 별도 실행에서 첫 방에 64마리를 지정했을 때 전원이 등장하고 프레임당 최대 생성은 4마리였다. 방 진입부터 등장 완료까지 p95는 6.52ms, 최악은 13.33ms였다. 전체 처치 뒤 다음 층으로 진행했다. `Invoke-CrowdMatrix.ps1 -Floors -RoomBurst -Seconds 2 -Runs 1`로 이 방을 재현한다. [강제 밀집 부하](../../Logs/Verification/FloorCrowd/Verified/large-crowd-1.json) · [실제 방의 웨이브와 층 진행](../../Logs/Verification/FloorCrowd/Verified/floors-burst-1.json)

웨이브 생성 한도까지 반영한 최종 빌드에서 같은 16마리 검사를 재실행했다. 이동·생성·피격·처치 p95는 차례로 5.49·5.46·5.95·4.78ms였다. 실행마다 전투 상황과 프레임 시간이 달라져 앞선 실행과 구분해 기록한다. [최종 빌드 재측정](../../Logs/Verification/FloorCrowd/ReleaseCheck/matrix-1.json)

64마리 첫 방을 포함해 한 프로세스에서 20층까지 연장해 매 층 전투 방 한 곳을 클리어했다. 동일 배치의 4~20층에서 머티리얼 42개·메시 1,006개·텍스처 168개·상주 루트 9개가 유지됐다. 4층 → 20층의 GC 후 관리 메모리는 22.71 → 22.83 MB, Unity 전체 할당 메모리는 243.22 → 243.30 MB였다. 중간 전체 할당은 최대 246.91 MB까지 변동했다. 입구 p95는 4층 4.07ms, 10층 4.03ms, 20층 4.02ms였다. 측정 프로세스는 종료 시까지 검사 결과도 메모리에 보관한다. ## 64마리 광역 적중과 동시 드롭

시드 907의 BattleScene 일반 방에서 64마리 웨이브를 생성했다. 플레이어의 원형 스킬 히트박스 범위를 넓혀 전원이 들어오도록 하고, 배치 후 0.15초를 기다려 물리 갱신과 공격 시간을 구분했다. 첫 적중·반복 적중·물리 트리거 적중·처치를 각각 2초간 측정했다. 처치 프레임에는 실제 보상 경로로 바닥 아이템 8개를 추가했다. 개발용 프로파일러를 끈 Windows D3D11 플레이어, Ryzen 9 9950X3D와 RTX 4060 Ti, 논리 640×360과 출력 1280×720에서 각 빌드를 세 번 새로 실행했다.

| 실행 후 첫 광역타 | 32.13ms | 26.83ms | 8.39ms |
| 같은 방의 반복 광역타 | 16.05ms | 11.47ms | 8.30ms |

각 열은 세 번의 실행에서 얻은 해당 지표의 중앙값이다. 수정 후 첫 적중과 동시 처치에서는 매 실행 각각 한 프레임이 16.7ms를 넘었다. 반복 적중과 물리 트리거에서는 해당 기준을 넘긴 프레임이 없었다. 네 구간 모두 적 64마리의 체력 감소 또는 사망을 확인했다. 수정 후 같은 타격 순간에 숫자 16개가 표시됐고, 두 프레임 안에 64개 전부 표시됐다. GPU 피격 입자가 나온 대상은 세 실행의 모든 구간에서 10마리에서 64마리로 늘었다. 방 클리어 뒤에는 시험 드롭과 일반 방 보상을 합쳐 아이템 9개를 한 번씩만 주머니에 넣었고, 골드는 200 증가했다. 추가 드롭 8개는 동시 부하 재현용이다.

재현은 검사용 Windows 플레이어 경로를 지정해 `Tools/Verification/Invoke-CrowdMatrix.ps1 -Player <exe> -Results <폴더> -AreaBurst -Seconds 2 -Runs 3`로 실행한다. `CombatPolish`에는 같은 시나리오 1회가 포함된다.

## 첫 광역타와 동시 처치의 프레임 예산

위와 같은 PC와 시드 907, D3D11, 640×360 논리 화면과 1280×720 출력에서 수정 직전 빌드와 최종 빌드를 각각 세 번 새로 실행했다. 웨이브 배치, 물리 안정화 대기, 공격 순서와 2초 측정 구간은 동일하다. 표의 실행별 수치는 각 구간에서 가장 오래 걸린 프레임이다.

| 64마리 전투 구간 | 수정 직전 3회 (ms) | 최종 3회 (ms) | 최종 p95 중앙값 (ms) | 16.7ms 초과 프레임 전 → 후 |
| --- | --- | --- | ---: | ---: |
| 첫 광역타 | 31.50 / 28.64 / 28.76 | 15.91 / 14.32 / 13.83 | 5.24 | 3 → 0 |
| 반복 광역타 | 15.91 / 13.93 / 12.49 | 7.71 / 6.85 / 7.63 | 4.89 | 0 → 0 |
| 물리 트리거 적중 | 12.20 / 11.27 / 11.42 | 6.83 / 6.70 / 6.94 | 5.03 | 0 → 0 |
| 동시 처치와 드롭 8개 | 24.84 / 22.12 / 24.36 | 11.19 / 12.64 / 11.69 | 3.29 | 3 → 0 |

첫 광역타의 동기 피해 처리 시간은 14.82~15.06ms에서 3.46~4.09ms로 줄었다. Mono 플레이어는 첫 던전 입장 때 전투 코드 컴파일을 여러 프레임에 나눈다. 숫자 전용 문자열은 서식 파서를 건너뛰고 표시 풀은 글리프와 모션 버퍼를 준비한다. 적의 피격 머티리얼 속성과 공용 타격 이펙트의 정렬·그리기 자원도 미리 준비한다. 카메라 반동으로 캔버스 갱신 알림이 와도 HUD의 실제 픽셀 경계와 색이 같으면 기존 메시를 쓰고, 같은 채움의 월드 체력바끼리는 벡터 메시를 공유한다.

처치 시 64개 Animator는 일반 애니메이션 갱신 시점에 사망 자세를 평가한다. 피해·사망 이벤트와 드롭 생성은 타격 프레임에 일어난다. 동시 처치의 동기 피해 처리는 7.59~8.04ms에서 4.38~4.41ms로, 바닥 아이템 8개를 실제로 생성하는 시간은 2.32~2.75ms에서 0.97~1.01ms로 줄었다.

최종 빌드의 12개 구간에서 각각 64마리가 맞고 64마리에 피격 섬광과 GPU 불꽃이 발생했다. 피해 숫자는 적중 시 16개, 두 프레임 안에 64개가 나왔다. 처치 때마다 기존 상한인 마무리 비행 6개가 재생됐고 시험 드롭 8개와 방 보상 1개를 각각 한 번씩 획득해 골드가 200 증가했다. 네 구간에서 측정한 총 7,184프레임이 모두 16.7ms 이하였다. 이 수치는 해당 PC의 짧은 동시 타격 재현에 대한 결과다.

플레이 모드에서 체력바 두 개가 같은 채움 메시를 사용한 뒤 한쪽만 20번 변경해 다른 쪽의 실루엣이 유지되는지 확인했다. 미니맵의 분수 좌표·회전·색상 변경 전후에 바닥과 그림자의 꼭짓점을 타일별 기준 좌표와 비교했다. 글꼴 검사는 프리팹 라벨 157개, 씬 인스턴스 530개와 비트맵 아틀라스 5개를 통과했다. 맵은 방 프리팹을 비동기로 생성하고 타일과 애니메이션 후보, 지형 그림자 메시, 스폰 위치를 여러 프레임에 걸쳐 준비한다. 기존 방 해제, 새 씬 활성화, 미사용 에셋 회수를 각각 실행한다. 완전 페이드 동안 월드의 정렬과 그림자 렌더링을 쉬고 공개 전 다시 그린다. 포탈은 비동기 GPU 읽기로 현재 캐릭터의 픽셀을 가져온다.

이전 층 탐색 메시, 두 층 이상 지난 방에서 층별로 한 개씩 표본 추출한 관리 객체, 남은 인계 씬은 GC 후 검사에서 모두 0개였다. 영속 루트는 9개였다. 4층과 20층의 Unity 할당량은 234.15와 235.05 MiB, GC 후 관리 힙은 22.71와 23.38 MiB였다. 이 값은 층 도착 시점의 표본이다.
